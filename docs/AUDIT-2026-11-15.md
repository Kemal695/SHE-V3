# SHE V3 — Engineering Audit & MVP Readiness Assessment

**Date:** 2026-11-15
**Scope:** Backend, firmware, mobile app, infrastructure. **Admin web excluded at the reviewer's request.**
**Method:** Static inspection plus live execution against the running stack and a physical `SHE-R24` board (MAC `10:06:1C:AE:53:28`, node `SHE-24-AE5328`).
**Reviewer note:** Every finding below was reproduced. Where a claim could not be verified, it is marked as such.

---

## 1. Verdict

**The project is not yet a minimum viable product. It is a credible single-home pilot.**

The engineering depth is real: 122 row-level-security policies, mutual-TLS device identity, a working command/telemetry loop, and a 33-screen app are not the work of a weekend. But three things separate "works on the bench" from "minimum viable product":

1. **Tenant isolation is not enforced on the message bus.** The database is isolated; the broker is not.
2. **Provisioning is fragile in a way a customer cannot diagnose.** It failed for seven independent reasons in one day, each silent.
3. **Supportability is missing.** No push notifications, no self-healing addressing, and a device that stores a wrong server address without complaint.

A user who is not the developer cannot currently install this product.

## 4. Findings

Severity: **Blocker** = prevents shipping to a second customer · **High** = causes outages or data loss · **Medium** = degrades operations · **Low** = cosmetic or documentation.

### F-01 · BLOCKER · The message bus has no tenant isolation

**Evidence**

```
emqx ctl conf show authentication   →   authentication = []
infra/docker-compose.yml            →   EMQX_LISTENERS__SSL__DEFAULT__ENABLE_AUTHN: "false"
infra/emqx-acl/acl.conf             →   30 rules, every one of the form {allow, all, …}
```

**Impact**

Any client holding a CA-signed certificate can subscribe to `she/+/+/+/+/telemetry` and publish to any device's `command` topic, across every tenant. The backend's 122 RLS policies are bypassed entirely, because the broker is the other door into the same data.

**Root cause**

`MqttAuthController` (`/internal/mqtt/auth`) denies any certificate CN that is not present in `device_certs`. The backend's own certificate (`she-backend`) has no row there, so enabling the authenticator would lock the backend out of its own broker. Authentication was therefore disabled to unblock development, which is defensible as a stopgap and indefensible as a shipped state.

**Remediation**

1. Register the backend certificate in `device_certs` (CN `she-backend`, ACTIVE, fingerprint from the issued cert).
2. Re-enable the HTTP authenticator using the correct EMQX 5 key form (`EMQX_AUTHENTICATION__1__…`, not `__DEFAULT`).
3. Replace `{allow, all}` ACL rules with per-tenant filters, or move authorisation to the backend `/internal/mqtt/acl` endpoint that already exists.

### F-02 · BLOCKER · A device can store a wrong server address and never recover

**Evidence**

The app sent its configured address, and the device stored it faithfully:

```
nvs: nvs_set_str mqtt_broker mqtts://192.168.1.21:8883
she_ble: she-net: broker = mqtts://192.168.1.21:8883
```

`.21` no longer existed. The intended safety net could not help:

```
she_disc: Broker unreachable — scanning 192.168.1.0/24 for the backend
she_disc: 1 host(s) answered but none looked like the SHE backend
```

Meanwhile `curl http://192.168.1.15:8080/actuator/health` returns `{"status":"UP",…}` (246 bytes) from the very host that was probed.

**Impact**

After any server address change, the device joins Wi-Fi successfully, then dials a dead host forever. From the app this is indistinguishable from a dead device. It required a manual firmware flash to recover.

**Root cause (two parts)**

- `net_discovery.c` matches the health body with `strstr(buf, "\"status\":\"UP\"")`. The probe reaches a host on TCP 8080 but the match fails, so a live backend is rejected as "not the SHE backend". The candidate IP is never logged, which is why this stayed invisible.
- The mobile app derives the broker from its own Settings → Server value. If that is stale, the device is given a dead address with no validation.

**Remediation**

- Log the candidate IP and the first 64 bytes of the response; accept HTTP 200 with a known header as a fallback signal.
- Have the app verify the backend is reachable **before** sending `she-net`, and fail loudly if not.
- Have the device validate that the received address is in its own subnet before persisting it.

### F-03 · HIGH · Persisted relay state can contradict the logical state

**Evidence**

```
ON  → she_inputs: Light 1 -> ON (lamp was OFF) — pulsing relay ch 0
    → she_relay: Saved relay state mask=0x000001

OFF → she_inputs: Light 1 already OFF — relay left alone
    → she_relay: Saved relay state mask=0x000001      ← unchanged
```

`relay_save_state()` (`relay_driver.c:865`) persists `relay_get_all()`, and `relay_restore_state()` (`relay_driver.c:851`) replays it at boot via `relay_set_all(state)`.

**Impact**

The API reports `Power:false` while NVS holds channel 0 as energised. On a 24-channel board switching mains loads, a reboot may drive a circuit the user believes is off.

**Remediation**

Make the mask derive from logical device state rather than the physical driver, and add a boot-time assertion that the restored mask matches the last reported parameter values.

### F-04 · HIGH · Deployment is not reproducible; secrets are committed as defaults

**Evidence**

```
infra/.env          → does not exist (only .env.example)
docker-compose.yml  → 9 occurrences of ChangeMeLocal / dev-internal-token
```

The missing `.env` left `EMQX_KEY_PASSWORD` empty, so EMQX could not decrypt its own passphrase-protected server key. Every TLS handshake aborted at ServerHello, and the client only saw `SSLEOFError` — which looks exactly like a bad certificate. This consumed several hours.

**Remediation**

Ship `.env.example` **and** a bootstrap that generates real secrets; fail fast at startup if a required secret is missing rather than degrading silently.

---

### F-05 · HIGH · No push notification transport

**Evidence**

No `firebase`, `FCM`, or equivalent reference exists in `backend/src/main/java` or `mobile/lib`. A notifications screen exists with no transport behind it.

**Impact**

Device-offline, alarm and automation events are invisible unless the app is open. For a smart-home product this is table stakes.

---

### F-06 · MEDIUM · Test coverage does not match the surface

| Layer | Surface | Tests |
|---|---|---|
| Backend | 125 endpoints | **5 classes** (`AuthControllerWeb`, `MqttAuthController`, `JwtService`, `GroupSetCommand`, `WriteParamsRequest`) |
| Mobile | 33 screens | 13 files |
| Firmware | 18 modules | **0** |

`.github/workflows/ci.yml` builds and tests the backend only — it contains **zero** references to `flutter` or `idf.py`. The two layers that broke most today are the two with no automated verification.

---

### F-07 · MEDIUM · The board is power-marginal

**Evidence**

Two flashes aborted mid-write with *"The chip stopped responding"*, leaving a corrupt app partition; both required a USB unplug/replug to recover. Writes of a few KB succeed; the 1.8 MB app image fails. Separately the chip rebooted with `rst:0xc` mid-session and dropped off Wi-Fi.

**Impact**

Field units may reset under radio + relay load. This also makes every firmware iteration slow and error-prone for the team.

---

### F-08 · MEDIUM · Billing and payments are stubbed

`BillingService` contains TODOs for PDF invoice generation, invoice email, dunning reminders, and daily reconciliation ("complete (stub)"). No payment provider integration was found.

---

### F-09 · LOW · Documentation overstates completion

Four `*SIGNOFF*` documents and 66 markdown files assert phase completion, while the core provisioning journey did not work end to end. Documentation that diverges from reality is worse than no documentation, because it ends investigation early.

---

### F-10 · LOW · Server address is compiled into the APK

The app is built with `--dart-define=API_BASE_URL=…`. When the server address changes, the app must be rebuilt or manually reconfigured — and if it is not, provisioning writes the wrong address into the device (see F-02).

## 7. Recommended path to MVP

Ordered by risk retired per unit of effort.

1. **Tenant isolation on the bus** (F-01). Register the backend cert, re-enable authentication with the correct EMQX 5 key form, scope the ACL per tenant. *This is the only finding I would call urgent — it is a data-exposure issue, not a UX one.*
2. **Address resilience** (F-02). Fix the discovery health probe, log candidates, validate the address in the app before sending it, and reject an out-of-subnet address on the device.
3. **Relay state integrity** (F-03). Derive the persisted mask from logical state; assert on boot.
4. **Reproducible deployment** (F-04). Real `.env` bootstrap, no committed secrets, fail fast.
5. **Push notifications** (F-05). Three events: device offline, alarm, automation fired.
6. **Test and CI parity** (F-06). Firmware host tests for command parsing and relay mapping; Flutter widget tests for the provisioning wizard; add both to CI.
7. **Second device, second home** (validation). Everything verified today was one board in one home.
8. **Power budget** (F-07). Measure the board under full relay + radio load; specify the supply in the installation guide.

Items 1–4 are what stand between the current state and an honest MVP claim. Items 5–8 determine whether it survives its first ten customers.
